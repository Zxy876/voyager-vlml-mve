## 0. 这是什么

一个跑得起来的**端侧大模型能力验证框架**：它**不训练模型**——参数永远不动——
而是让 agent 在真实数据库环境里**自己出题、自己取数、自己被判卷、
把跑通的做法结晶成技能**，再用消费线检验：换一个模型接进来，已学技能还在不在、
答案还判不判得对——**差距就是该模型在这个环境里的真实能力**。

**习得是手段，验证是目的。** 被测对象是接入的 LLM；技能库、判官、
防幻觉闸都是量具。这套设计源自 Voyager（Wang et al., 2023）开创的范式：
把"学习"从改模型权重换成**改可执行的技能库**——环境反馈不回传梯度，
而是回传一个**判卷结论**；经验不是存成样本对，而是结晶成
**可检索、可组合、可重放的程序**。
原版在 Minecraft 里验证，本仓库把它搬进**真实数据库世界**并做成了
**按场景隔离、可插拔泛化**的通用框架：

> **一句话：换一个数据源 + 注册可执行动作，同一个学习引擎就能在新领域
> 从零开课——这就是 1→n。**

| | 原版 Voyager | 本系统（MVE） |
|---|---|---|
| 环境 | Minecraft（视觉/方块） | 真实 DuckDB/SQLite 数据库 + 本机文件 + MCP 工具 |
| 动作空间 | JS 代码调 Mineflayer API | SQL / Python 调 `query_sql`、MCP、本机只读原语 |
| 学习信号 | 环境事件 + 自我判卷（critic） | **真实取到数没有** + critic + 三道确定性守卫 |
| 经验结晶 | JS 技能库（Chroma 向量检索） | SQL 配方库（embedding 检索 + 字面量守卫） |
| 泛化评估 | 无（开放世界） | **消费线**：人问一句，用已学能力作答，判掌握 |

## 1. 核心循环（技能习得机制）

```
                    ┌─────────────────────────────────────────┐
                    │              ① 课程（出题）              │
                    │   人导入里程碑 / 自动课程最弱优先推进     │
                    └───────────────────┬─────────────────────┘
                                        ▼
   ┌──────────────┐   decompose   ┌─────────────────────────────┐
   │ ② 技能检索    │◄─────────────│ ③ rollout（执行层）          │
   │ embedding 盲取│───注入──────►│ 写 SQL/代码 → 真实取数       │
   │ top_k（原版   │              │ 内层 4 步迭代（critic 反馈    │
   │ 同构）        │              │ 进 context 槽，原版同构）     │
   └──────────────┘              └──────────┬──────────────────┘
            ▲                               ▼
            │                     ┌─────────────────────────────┐
            │                     │ ④ 判卷（三道确定性闸 + critic）│
            │                     │ 字面量守卫 / fan-out 闸 /     │
            │                     │ 真空防线 / LLM 判官           │
            │                     └──────────┬──────────────────┘
            │                                ▼
   ┌────────┴─────────┐            ┌─────────────────────────────┐
   │ ⑥ 复用消费        │            │ ⑤ 经验结晶（成功才写库）      │
   │ 多配方整批编排     │            │ 泛化成 :slot 模板存算法不存值 │
   │ → 守卫 → 取数     │            │ 维度原子技能 + 里程碑复合技能 │
   │ → 叙事聚合 → 掌握 │            │ 图谱节点 + 掌握度账          │
   └──────────────────┘            └─────────────────────────────┘
```

每一环都与原版 Voyager 同构（逐条对照见 §3），且全部经验可在线累积：
**清库归零重学是可重现的实验**（面板一键），学完账本可审计、可回放。

## 2. 两条线，一套能力，两个判据

| | **学习线**（`scene_learn` → `learn_orchestrate`） | **消费线**（`consume.py`） |
|---|---|---|
| 谁出题 | 里程碑课程（人导入 / 自动出题器推进） | **人写一句想问的话** |
| 它做什么 | 拆维度 → 逐维度 rollout → 取真数 → 结晶技能 | **用已积累的能力回答**（多技能编排复用） |
| 成败判据 | `success` = 真的从 DB 取到数（非真空值） | 取到真数 + 叙事给出有据回答 |
| 算不算分 | **不算**覆盖率、不算掌握度 | **从这里开始算**覆盖率与掌握度 |
| 判分给谁看 | 不给任何人（它自己看 DB） | **只给人看**，绝不回灌学习线 |

两条线共用同一套技能库与图谱，但**账本分开**：练习不判分，消费才判分。
这是有意的——判分的尺子不能进学习反馈环，否则它学会的是"讨好裁判"，
不是"取到数"。

**掌握度 = 能力集合的增长，不是分数**：`已掌握能力项 / 该掌握总量`。
重复导入同一问题，第二次复用已学配方答出来 → 掌握度上升，且面板能说清
**涨的那一分来自哪次导入长出的哪条技能**。

## 3. 与原版 Voyager 的同构对照（逐条，file:line）

| 原版机制 | 原版位置 | 本系统对应 |
|---|---|---|
| 自动课程 `propose_next_task` | `curriculum_agent` | 出题器：里程碑锚点优先 → 最弱优先自动出题 |
| 子目标分解 + 逐个完成 | `voyager.py:403-435 inference` | Maieutic 追问骨架拆维度（骨架吃 DB 实查，防编参数），逐维度 rollout |
| 每轮先检索技能再执行 | `voyager.py:195/199` | `skill_store.retrieve()`：**embedding 余弦盲取 top_k**（原版 Chroma 同构，无词面门槛），学习侧与消费侧同一函数 |
| 整批注入执行层 | `action.py:94 programs` | 检索到的配方整批注入 `agent.solve`，agent 按需组合 |
| critic 反馈进下一轮迭代 | `:231-234 render_human_message(critique=)` | 内层 4 步迭代 + 里程碑重试轮 critique 进 context 槽（`_hint_ctx`） |
| 内层动作级重试上限 | `voyager.py:30 task_max_retries=4` | `solve` 4 步迭代，外层每任务默认 1 次 rollout（原版同款双层） |
| 成功才写技能库 | `voyager.py:230 add_new_skill` | 入库三道关：字面量守卫 → fan-out 闸 → 真执行取到真数，缺一不入 |
| 原子技能组合成复合 program | `learn()` 第二步 | 里程碑全闭合 → 组合复合技能入库（`learn_milestone_composite`） |
| 存算法不存数值 | 技能即程序 | `generalize_sql_recipe` 泛化成 `:slot` 模板，回填时只填**库里真实存在的取值** |

### 在原版之上的四个增量

1. **防幻觉三闸**（原版没有，真实数据库必需）：
   - **字面量守卫**：SQL 里每个筛选值必须能在 `db_observation` 实查清单里指认
     （范围谓词的日期边界豁免——月末 cutoff 不在数据取值域里是正常的）；
   - **fan-out 闸**：跨一对多 JOIN 把驱动表行放大再聚合 = 乘爆，确定性拒绝；
   - **真空防线**：空表聚合返回 1 行 `(NULL, 0)` 不算取到数，bool 是 int 子类也拦。
2. **场景隔离 1→n**：技能带 `source_scene`，检索按 `{本场景, default}` 过滤；
   换数据源 = 注册新场景，学习引擎零改动；清库按钮可一键把单个场景的
   课程账 / 骨架 / 锚点 / 技能清到归零重学。
3. **消费多技能编排**：合成题（工资+津贴+加班）不再被单条配方答掉——
   检索到的**每条**相关配方都实例化成 SQL，逐条守卫、逐条执行取真数，
   合并交给叙事层聚合组织，来源技能逐条编号披露。
4. **里程碑重试有上限、失败换题（2026-10-31 按原版 learn() 修正）**：前置维度
   全闭合后对里程碑本体重跑（已闭合维度不重学），取到真数才点亮解锁——
   不点亮语义保留，假掌握没有漏出路径；但连败 4 次（=原版单任务重试上限
   `action_agent_task_max_retries`）即按原版 `update_exploration_progress`
   记 failed + "Skipping to next task."，挂冷却先换题、冷却清零再回来攻
   （不判死，failed 也留在账上）。原版没有"整题总验收"层
   （`inference()` 完成判据=最后一条子目标成功），无限原地重试是自造死循环，
   实测曾 26 轮同一题。

## 4. 学习线：一轮发生了什么

```
人导入「九月份公司要往外支出多少钱」
  → Maieutic 拆维度（吃 DB 实查：只指向真实表/列）
     ① 技术部 base_salary 合计   ② 餐补交通补贴总额
     ③ 加班工资总额              ④ 请假补偿总额
  → 逐维度 rollout：写 SQL → query_sql 取数 → critic 判 →
    跑通一条入一条原子技能（泛化 :slot）
  → 全闭合 → 里程碑本体重试（对题目本体 rollout，不重学已闭合维度）
  → 取到真数 → critic 收口 → 点亮解锁 → 组合复合技能入库
```

课程推进同原版 `learn()`：任务失败进 failed 账换下一个；人导入的题是
manual 语义，失败沉底重试；连续超时收工；墙钟断点续学。

## 5. 消费线：一次回答发生了什么

```
人问一句
  → 归题（图谱检索 + 能力项归属）
  → embedding 检索本场景已学配方（盲取 top_k）
  → 无已学 → 如实标「未学」，交给学习线拆解，绝不现做合成
  → 有已学 → 多技能整批编排：
      每条配方 → 回填 :slot（值必须逐字来自实查清单）
      → 字面量守卫 / fan-out 闸 逐条拦 → 逐条执行取真数
  → 数据行标「来源技能」→ 叙事层聚合（来源编号逐个披露）
  → critic + 裁判独立复核 → 掌握度记账（能力集合 +1）
```

**消费只编排复用，不现做合成**——这是 2026-10-25 拍板的边界：
学过什么答什么，没学过就明说"未学"并踢回学习线。"未学"的反面
不是"编一个答案"，是"标记 + 生成课程"。

## 6. 数据契约：agent 的产出是事实集，不是一段话

Voyager 每轮产出：**SQL + 真实行数据 + 来源工具清单 + 判卷结论**。
叙事（给人看的自然语言回答）单独一层产出，且**声明不参与判分**——
判分只看：取到真数没有、方法与裁判比对是否同量、字面量是否全部可指认。

## 11. 诚实标注

- 掌握度不是分数，是**能力集合计数**；覆盖率是只给人看的质量分，不进反馈环。
- 本框架**不训练模型**：无梯度、无回放缓冲、无神经奖励模型——参数永远不动，
  动的是技能库。"学习"指 Voyager 范式的**在线技能习得**：环境反馈不回传梯度，
  而是回传判卷结论；通过判卷的经验结晶成可检索、可组合、可重放的技能——
  技能库替代参数更新，判官 + 确定性守卫替代奖励信号。
- 与 RL 的对应（episode / horizon / policy / critic）只是**同构分析视角**
  （Tianshou 对照），帮熟悉 RL 的开发者快速定位组件；本项目不做强化学习
  训练，不与 Deep RL 混称。框架的目的是**验证**端侧大模型在此闭环中表现出
  的"会了"是真技能还是幻觉——习得是手段，验证是目的（2026-11-01 定位：
  面向开发者的端侧大模型能力验证框架）。
- 所有同构对照均给出原版 file:line（参照源码在 `voyager_original/`）；
  自定项（无原项目背书的设计）均在代码注释里逐条标明。
- **判分是软尺子，且裁判是 LLM 判 LLM**（2026-11-02 澄清）。消费判分的主尺子是
  「两边做法的比对」（LLM 判），不是题库既有 rubric；裁判自己会跑偏（问击杀数
  它去算 K/D），跑偏时只能**如实显示没判到**。方法论上这里有内在张力：用模型判
  模型「是不是真会了」，比「没有验证」强，但**离「可信的能力基准」还有距离**。
  确定性守卫（真空防线 / 来源绑定）管得住「材料真假」，管不住「口径对不对」——
  口径层面目前靠判词披露，不靠硬保证。
- **「迁移考核 0%」是已弃用的标准，不是活跃缺口**（2026-11-02 澄清）。技能绑死题目
  （调用序列写死 `series_id` / 图名）是事实；但「跨题迁移考核」属于早期考核线的
  验收口径，**现已不再使用**——2026-11-01 定位改写后，能力验证走消费线
  （人问一句、用已学能力作答、判掌握），不以「换个参数还能不能做出来」为验收
  标准。「换值回测」（防单库对答案假阳性的入库后佐证）目的与此不同，不受影响。
- **技能的 `code` 字段混装 SQL 与 Python，`kind` 字段缺失，读取端各假定一种**：
  场景 A 的纯 SQL 到学习侧会被当 Python `exec()`。db 落库三表方案
  （`problem` / `plan_ref` / `recipe`，`docs/建模表与技能落库-可行性.md`）
  **已设计完成、待实施**——知道怎么修，还没修。
- **消费侧两条入口的防幻觉完整度不同**（2026-11-02 复核）：`consume.py` 接了真空
  闸三（`has_real_data` × 4），但缺 `source_binding` / 搬运判据 / 示范召回；
  `coach.explain`（面板聊天 + 人导入）只有 no_call 级闸，**2026-11-02 拍板不再加**
  ——它是探索入口不是判分入口，产物是候选题（落盘前过 `generate_adopt` 验题闸），
  规则加一条、探索的自由度就少一分。待补的是 `consume.py` 侧的判分完整度，
  不是给 explain 加闸。
