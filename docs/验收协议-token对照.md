# 验收协议：token 对照（同 agent 前后配对）

> 2026-11-03 拍板口径：**对比同一个 agent、同一个任务上前后两次的 token 消耗。前者已超支（烧完未达成），
> 后者带 MVE 配方不超支且达成，即优于前者。**
>
> 本文把这个口径写成可执行判定，包括三个必须先钉死的前提——否则结论会来自人的记忆，而不是 MVE 的配方。

---

## 一、指标：用「每个达成任务的 token」，不用「省了多少」

基线那次是**烧完预算仍没解出来**。所以它的有效产出是 0，不是「消耗了 X」。

$$TPS = \frac{\text{本次会话累计 token}}{\text{达成任务数}}$$

| 运行 | token | 达成 | TPS |
|---|---|---|---|
| ① 基线 | 触顶预算 | 0 | **∞** |
| ② 原人 + 配方 | ≤ 预算 | 1 | 有限值 |
| ③ 干净会话 + 配方 | ≤ 预算 | 1 | 有限值 |

只要达成且不超支，`TPS < ∞` 就恒成立。**所以"优于"不需要统计，不需要算百分比，它是一个严格成立的不等式。**
这就是这个口径最大的好处：把需要大样本的均值比较，降级成一次真实使用里就能观察的翻转。

不要说「省了 40%」——基线省不出来，它是从 ∞ 到有限。

---

## 二、三个必须钉死的前提

### 前提 1：同一条预算线

前后两次用同一个阈值。它可以是单任务会话的 token 上限、agent 的上下文窗口比例、或团队设定的单任务成本。
**线一旦移动，"不超支"就失去意义。** 每次对照必须在记录里写明这条线的取值和来源。

### 前提 2：配方自身的成本计入

带 MVE 方法 = 上下文里多了一段配方文本（`sql` + 工具依赖 + 口径说明），这是额外输入 token。
**不计入就是作弊**：任务本体 8k、配方 1.5k，只报 8k 说"没超支"，等于把成本挪到了看不见的地方。

记账时把条形拆成两段：`任务本体` + `配方注入`。配方长度可由 MVE 侧直接量出
（技能记录里的 `code` 与描述文本），这也是 MVE 唯一需要报的数。

> 可行性红线：`配方 token / 预算` 若超过 20%，这次迁移在账上就不划算——不是配方错，是场景不合适。

### 前提 3：人的记忆要隔离

这是最容易被忽略、也最容易把结论搞反的一条。

第一次失败后，**人已经知道哪条路不通**。第二次省下的 token 可能来自人的知识，而不是 MVE 的配方。
用户自己的判断也是这个结构：「人和 agent 协作有磨合，要么人进步，要么模型进步」。所以必须分清是哪一种。

因此要跑**两组**，不是一组：

| 组 | 配置 | 能证明什么 |
|---|---|---|
| ② 原人 + 配方 | 踩过坑的人，看得到配方 | **弱证据**。省了，但可能是人记住了答案 |
| ③ 干净会话 + 配方 | 新会话 / 不知情的人，只有配方 | **强证据**。省了，说明配方是可交付资产 |

**只有 ③ 通过，才算 MVE 的贡献。** ② 通过而 ③ 不通过，说明价值留在人身上——那 MVE 只是个记事本，不是配方工厂。

这也顺带定义了 MVE 的产品形态：配方必须**脱离人也能用**。若必须由踩过坑的人翻译一遍才生效，它就没通过交付性检验。

---

## 三、记账清单（两边各记什么）

MVE 侧不记运行 token（已拍板：账在 agent 那边，两本账必然对不上）。MVE 只报一项：

- **配方 token 长度**（`code` + 描述 + 口径文本，按 agent 的 tokenizer 折算）

agent 侧记六项，前后两次用同一张表：

| 字段 | 说明 |
|---|---|
| `tokens_in` / `tokens_out` | 分开记，缓存命中单列（cache read 便宜一个量级，混记会失真） |
| `turns_failed` | 失败轮数 |
| `tool_calls` | 工具调用次数（往返次数比 token 更早暴露问题） |
| `recipe_tokens` | 本次注入的配方长度；基线为 0 |
| `solved` | 达成 / 未达成——**必须可判定，不能是"感觉差不多了"** |
| `budget_line` | 本次使用的预算线取值 |

---

## 四、摊销：单次不超支是必要条件，不是全部

MVE 学习那一轮的成本 `L` 不在这条线里。它要摊到复用次数上：

```
单次净节省  Δ = budget_line − (任务本体 + 配方注入)
回本次数    n* = L / Δ
```

- `n* = 3`：这条配方很快回本，值得留。
- `n* = 50`：这条配方只对极高频任务有意义。
- `Δ ≈ 0`：**"技能省 token"这一半价值是伪命题**——MVE 只剩"暴露 agent 缺陷"那一半，而这本身也是有价值的产出。

所以验收要报两个数：**单次是否不超支**（翻转判定），**n\* 是多少**（经济性判定）。只报前者，容易把一次侥幸当成方法有效。

---

## 五、什么时候这个对比不成立

出现任一情况，结论作废，不要硬解释：

1. **换了 agent**（模型、工具面、系统提示任一不同）——工具名不同构会直接撞在调用层，不是推理层。
2. **换了任务**——难度不可比，必须同一道题。
3. **人未盲**——② 组结论只能算弱证据，不能当验收依据。
4. **配方未计入**——条形少一段，结论虚高。
5. **只跑了一次**——单次受运气影响。折中做法：同一任务换 3 种表述各跑一次，三次都达成且都不超支才算过。

## 六、判定表（照填即可）

| 项 | ① 基线 | ② 原人+配方 | ③ 干净会话+配方 |
|---|---|---|---|
| 预算线 | | 同 ① | 同 ① |
| 任务本体 token | | | |
| 配方注入 token | 0 | | |
| 合计 | | | |
| 是否越线 | 是 | | |
| 是否达成 | 否 | | |
| 工具调用次数 | | | |
| 失败轮数 | | | |
| **判定** | TPS = ∞ | 弱证据 | **强证据（验收依据）** |

结论只有三种：

- **③ 达成且不超支** → 验收过。配方是可交付资产，进入 `n*` 计算。
- **③ 达成但超支** → 配方能用但要瘦身（裁剪 `code`、去冗余口径），属适配问题，不是学错。
- **③ 不达成** → 学错了。回查这条技能的 `provenance`：它是从 web 缓存学的、还是从上传文档学的。web 来源的配方通常可搬（纯文本 claim），`query_sql` 来源的要看 agent 侧有没有等价工具。

## 七、这套协议对 MVE 的要求

它不要求 MVE 增加埋点（已拍板关闭），但要求两件已经在做的事保持住：

1. **技能必须能被搬走**——`code` + 工具依赖 + 口径要能整段取出，不能依赖 MVE 内部状态。11-03 加的 `provenance` 正是搬运前的可行性判据。
2. **达成与否必须可判定**——不能由 MVE 自己说"这次学好了"。判据在 agent 侧的执行结果上，不在 MVE 的 `verdict` 上。

否则就回到了那句话：框架承诺能力，仪器承诺测量。**测量必须发生在被测量的地方。**
