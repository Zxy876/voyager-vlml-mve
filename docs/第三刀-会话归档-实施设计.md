## 一、调研结论（原版 maieutic，只读取证，全部亲自复核到 file:line）

调研对象：`~/maieutic`（origin `https://github.com/bcanata/maieutic.git`，HEAD `8e6f7ee`）

### 1. 原版**没有「归档」这个概念**（全仓零命中）

```
$ grep -rn "archive\|归档" src/ prisma/     → 0 命中
```

原版的「归档」= 三件事同时发生（`src/lib/sessions.ts:222-249` `advancePhase`）：

```ts
await prisma.session.update({ where: { id: sessionId },
  data: { currentPhase: to, ...(to === 4 ? { completedAt: new Date() } : {}) } });
await appendSessionEvent(sessionId, "phase_transition", { from, to });
```

即：`currentPhase = 4` + `completedAt` 非空 + 一条 `phase_transition` 事件。
**没有归档表、没有归档文件、没有快照拷贝。** 会话内容全在 `Session` 一行的 4 个 JSON 列里。

### 2. 原版**没有多代理派单机制**

```
$ grep -rn "subagent|dispatch|delegate|taskId|orchestrat" src/   → 0 命中
```

「派任务 vs 验收」在原版对应的是**同一个学生回合里的两次独立 LLM 调用**：

| 角色 | 原版位置 | 机制 |
|---|---|---|
| 生成 | `intent-diff`（`src/app/api/session/[sid]/submit/route.ts:64`） | LLM 产出分歧点 |
| 判定 | `post-hoc`（`src/app/api/session/[sid]/divergence-response/route.ts:67`） | LLM 二次裁定，**独立提示词** |

而「整体是否完成」是**确定性代码**判的（`src/app/api/session/[sid]/spec/route.ts:85`）：

```ts
const passed = examiner.gaps_still_open.length === 0;
```

模型输出的 `passed` 被**丢弃**。→ 对应 MVE 的 `milestone_state`（`maieutic_scaffold.py:1084`
`achieved = (bool(total) and not missing) or achieved_flag`）。

### 3. 原版**没有「换个问法」的机制**，因为需求身份不是文本

- 需求身份 = `Exercise.id`（**slug**，教师发布时 `slugify(title)`，`prisma/schema.prisma:14`）
- 会话身份 = `Session.id`（cuid）
- 复用 = `findOrCreateSession(exerciseId, studentId)`（`sessions.ts:159-170`）**精确二元组匹配**
  + `resolveSession()`（`sessions.ts:132-157`）**纯函数**：优先可续的未完成 > 最后完成后的空会话 > 最近的已完成
- 恢复的上下文 = `Session` 的 4 个 JSON 列 + `currentPhase`

```
$ grep -rni "md5|sha256|similarity|embedding|fuzzy|levenshtein" src/   → 0 命中
```

**原版全仓无任何相似度/哈希检索。** 因为需求是教师**预先发布**的固定 Exercise，
`Session.id` 由 URL 显式传递，根本不需要「找回同一需求」。

### 4. 教师端生成一次 → publish 快照 → 运行时只读

| 阶段 | 位置 | 行为 |
|---|---|---|
| 生成 | `src/app/api/author/generate-scaffolding/route.ts:29-46` | **不写库**，只返回 JSON |
| 发布 | `src/app/api/author/publish/route.ts:19-28` | **永远 CREATE 不是 UPDATE**；id 冲突加随机后缀 → 改一版题目 = 两个 Exercise 行 |
| 落库 | `createExercise`（`sessions.ts:44-64`） | 一次写最终维度 + Opus 原始轨迹 + `publishedAt` |
| 运行时 | `src/app/api/session/[sid]/spec/route.ts:48-70` | **只读** `exercise.specGateDimensions` |

```
$ grep -rn "scaffolding" src/app/api/session/   → 0 命中
```

运行时**零命中** scaffolding —— 这是「骨架拆一次就固定」在原版的物理保证。

### 5. 原版的持久化面只有 4 张表

`prisma/schema.prisma`：`Exercise`(13) / `ExerciseTranslation`(42) / `Session`(54) / `SessionEvent`(76)

- 会话内容全在 `Session` 的 `phase1Data` / `phase2Data` / `phase3Data` / `liveSummaries`
- 唯一 append-only 轨迹表 = `SessionEvent`
- LLM 调用**只 `console.log`**（`src/lib/opus/client.ts:35-37,46-66`），**不含正文**
- 代码执行输出**只在浏览器 React state**（`ExerciseClient.tsx:116`），**不落库**
- 冻结语义：`recordFinalRevision` 注释 —— 修订不动 `phase2.finalCode` / 分歧答案 / 分类（那是冻结的学习信号）

### 2.3 派任务与验收混淆的确切位置

`voyager_vlml/consume.py:2437-2477`：

```python
if data is None and _use_env and not auto_learn:      # 回访模式
    learn_kick = {"kicked": False, "manual": True, ...}
```

同一个 `data is None` 同时承担两个语义：

对照原版：**验收的判据是 `gaps_still_open.length === 0`（需求级），

## 四、改造方案（照抄，不发明新打分/门槛机制）

### 刀 A：需求级 id（会话身份的载体）

**问题**：现在所有键都挂在问句 md5 上 ——
`_cache_path` = `md5(question)[:12] + "_" + md5(db_path)[:8]`（`maieutic_scaffold.py:243-258`）
→ 换问法 = 换骨架 + 换闭合账 + 换会话 key。

**照抄原版**：原版需求身份 = `Exercise.id`（slug，发布时定，运行时不改）。
MVE 的对应物 = **需求级 id**，由**人导入那一刻**生成并固化，之后换问法不改。

**落点**（不新增第二套账，全挂在已有图谱节点上）：
- MVE 已有 `import:<批次id>` 节点（`maieutic_scaffold.py:1375`）= 一次导入批次
- 已有 `consume:<topic_id>` 节点（`:1363`）= 一道题
- **缺的是「需求」这一层**：同一个需求被多次用不同问法问，应该落到**同一个**需求 id

**做法**：给需求一个显式 id（`req_<hash>` 或复用图谱节点 id），
让 骨架 / 进度三本账 / 追问历史 / 技能归属 / 会话归档 **全部挂它**，
而不是挂 `md5(question)`。

**这是任务 269**（MEMORY 已记，pending）。链路已查清：
`import_id`（时间戳批次）≠ 需求身份；`routing.route` 已能给 `node_id`/`node_label`。

### 刀 B：会话归档（原版同构）

照抄原版的三件套，**不加新表**：

| 原版 | MVE 对应 | 做法 |
|---|---|---|
| `Session.currentPhase`（1/2/3/4） | 会话阶段 | 会话记录里加 `phase` 字段 |
| `Session.completedAt` | 归档时刻 | 会话闭合时写时间戳 |
| `SessionEvent`（append-only） | 会话事件流 | 事件追加写，不覆盖 |
| `Session.phase1Data/2Data/3Data` | 会话内容 | 骨架 + 闭合账 + codes + iterations |

**落点**：会话 = 一次「解决一个需求」的过程记录。
现有 `progress.codes`（含 code/answer/r/how）+ `progress.iterations`（追问历史）
+ `progress.learned`（闭合账）**已经就是会话内容**，只是键挂在问句上、且没有状态机。

**做法**：给会话记录加 `phase`（学习线内部用）+ `completed_at`；
闭合一条维度 = 追加一条事件，不覆盖。

### 刀 C：召回会话而非技能

**照抄原版的方向**（`findOrCreateSession` 精确匹配 + `resolveSession` 纯函数选会话）：
1. 消费侧先按**需求 id**（刀 A）找会话 —— 不是按问句向量检索技能
2. 命中会话 → **直接用会话里的 code/answer/r**（验收结果已在学习侧跑完）
3. 会话里 `answer` 已有的维度 → **不重跑**，直接披露
4. 会话未闭合的维度 → 只对这部分派任务（学习侧继续攻）

**这一刀同时解决用户的第 1 点**：验收（读会话里已验过的 answer）与派任务
（只对未闭合维度派）**在数据源上就分开了**，不再靠一个 `data is None` 猜。

### 刀 D：披露验收结果

`progress.codes[].answer` 现在是死数据。刀 C 接通后：
消费侧答得出来时，优先用会话里已验过的 answer（带 r、带 how），
**不重跑 SQL、不重判**。这就是「验收已经在学习侧跑完，只是没有答案披露」的兑现。

### 踩到的三个坑（都已写进代码注释与 MEMORY）

1. **`req_id_of` 的 `allow_alloc` 默认必须是 False**
   默认 True 时，「读一次骨架路径」就会凭空造出一个需求 ——
   `_cache_path` 走的是读路径（16 处调用点全是读/写进度账），
   分配副作用会污染登记表，且让「没登记的题」也落到 req 键上（零回归被破坏）。
   **分配只在明确的写入口发生**：人导入那一刻。

2. **req 登记必须排在路由读骨架之前**
   骨架键挂在 req id 上 → 读骨架之前身份必须先定下来，否则读到的是「还没登记」的空账。

3. **消费侧登记不许拦消费**
   身份登记是增强，不是门槛（同 `on_miss` 的既有口径）。

## 六、执行顺序与风险（历史，已完成）

| 刀 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| A | 需求级 id 替代问句 md5 | — | **高**：键迁移，旧骨架文件要迁移/兼容 |
| B | 会话 phase + 事件流 | A | 低 |
| C | 召回会话而非技能 | A、B | 中：消费侧检索路径改造 |
| D | 披露已验答案 | C | 低 |

**建议顺序**：A → B → C → D。A 是根，其余三刀都在它上面。

**A 的迁移注意**：
- 旧骨架文件键 = `md5(question)[:12]_<md5(db)[:8]>.json` → 新键 = 需求 id
- 迁移策略：**读时兼容**（新键找不到 → 按旧键回退找一次 → 命中则**迁移**并留证），
  不一次性重命名（避免把不同需求的旧骨架混成一个）
- ⚠️ 旧键回退必须用**当前问句的 md5**，不能扫目录取最近（那会拿到别的需求的骨架）

**测试要钉死的**：
- 同一需求换问法 → 骨架**不重拆**（维度 id 一致）
- 换问法 → 闭合账延续（learned 不丢）
- 召回单位是会话 → 命中会话即带出全部组成技能（不只是命中那条）

## 七、实施记录

### 刀 A：需求级 id（req id）

**设计要点**

1. **req id 的生成与落点**
   - 人导入那一刻生成 `req_<md8(规范化原句)[:12]>` —— **与问句解耦的关键**：
     规范化 = 去空白 + 全角半角统一 + 标点归一，**不改词序、不改字**。
     换问法（改词序/加字）→ 规范化后不同 → md5 不同 → 仍是新 req。
     ⇒ **这意味着 req id 本身也解决不了「换个问法」**！
     ⚠️ 实测：三个问句「帮我查查用户名 ce 的这位女生…」「username为ce的女生…」
     「查一下ce这个用户…」规范化后互不相同 → req id 必然不同。
   - ⇒ **修正**：req id 不能由问句派生，必须**独立于问句**产生。
     照抄原版：`Exercise.id` 是**教师发布时给的 slug**，不是从题目文本算出来的。
     MVE 的对应物 = **人导入那一刻系统分配的一次性 id**（时间戳 + 随机后缀），
     之后**永不改变**；「换个问法」要回到同一个 req，
     靠的是**归题（routing）找回这个 req**，不是靠文本相同。
   - ⇒ 因此刀 A 实际是两件事：
     **A1 生成**：人导入 → 建 `req_<时间戳><随机>` 节点（图谱里 `kind="req"`），
        记 `req_id ↔ 原始问句` 的映射。
     **A2 归位**：新问句到来 → `routing` 归题 → 找到已有 req 节点 → 复用它的 req_id。
        这正是 `routing.match` 的活（它已经在做「找回同一道题」），
        只是现在找回的是 `consume:` / `import:` 节点，要扩到 `req:` 节点。

2. **键的迁移**（读时兼容 + 自动迁移）
   - 新键：`CKPT/<scene>/req_<req_id>.json`
   - 旧键：`CKPT/<scene>/<md5(question)[:12]>_<md5(db)[:8]>.json`
   - 读新键找不到 → **按当前问句的 md5** 回退找旧键 → 命中则**迁移**（写新键 +
     旧文件改名留证 `.migrated<ts>`）→ 返回
   - ⚠️ 回退**只能用当前问句的 md5**，不许扫目录取最近（会拿到别的需求的骨架）

3. **不变的东西**（守既有铁律）
   - 骨架**拆一次就固定**：req id 一旦绑定骨架，改问法回来读到的是**同一份**
   - 进度三本账（learned/codes/iterations）同住一个文件 → 换问法延续
   - 维度 id 稳定 → 闭合账对得上
