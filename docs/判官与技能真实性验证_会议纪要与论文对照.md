# 判官与技能真实性验证：会议纪要 × 两篇论文 × MVE 对照

> 2026-10-29 有道会议《AI 判官与技能学习验证框架讨论》纪要 + 论文对照。
> 论文原文：`2306.05685v4.pdf`（LLM-as-a-Judge）、`2010.02840v1.pdf`（Text-to-SQL Test Suites）。
> 本文是 2026-10-31 按会议行动项整理的第一版。

## 0. 一页纸：MVE 到底在验证什么

MVE/Voyager-VLML 不训练模型、不改权重。它做的事情是：**给一个外接的 LLM 套上
"拆维度 → 取证 → 判官把关 → 技能入库 → 复用"的闭环，然后回答一个问题——
模型在这个闭环里表现出来的"会了"，是真的学到了可复用的技能，还是碰巧答对/幻觉。**

- 判官（reward）= 另一个 LLM + 确定性闸门，不是神经 reward model；
- 技能 = 验对轨迹的沉淀（SQL 配方 / Python 程序），存算法不存数值；
- 验证对象是**架构**，不是模型：换掉外接 LLM（flash ↔ glm-4.6）整个闭环照跑，
  所以它能当"任意小模型的学习能力测试台"用（2026-10-31 实测：同一份代码，
  flash 卡在 KeyError: 0 四步重犯、里程碑点不亮；换 glm-4.6 后 0 错误、里程碑
  首次点亮——这本身就是"模型能力差异被框架如实反映"的一个直接证据）。

## 1. 会议拍板的方向（2026-10-29）

1. **不做强化学习/训练**。技能积累不依赖微调权重（这正是选 Voyager 的原因）；
   "往 RL 方向去想"的上一版想法收回。
2. **大模型当判官**：拆维度（任务是否做对）、判官（reward 是否给过）都可以由
   LLM 承担，AI 评价 AI。
3. **漏检/错检不可避免**（第一类/第二类错误），人判也一样；不追求零漏检，
   把"以大模型为中心的判定框架"这个概念立住就够了。
4. **防幻觉机制要内嵌在学习过程里**，而不是单独拎出一个测试机制
   （导师原话：你这个框架反而比他们那种单独拎出来做测试的框架好）。
5. **模型外接是特性不是缺陷**：要验证的是"架构 + 学习过程"，模型能力本身
   已被各家验证过；换模型就能测"这个模型是否真的有学习能力/是否被幻觉污染"，
   面向的开发者场景就是各领域小模型的自证。
6. **消费侧 + DeepSeek 重构不多余**：不做就无法区分"模型自己给的"和"真正复用
   技能"的答案。
7. 行动项：① 把框架和拆维度等细节整理成文档放 GitHub；② 对照两篇论文，
   看内容差距；③ 用论文思路佐证"学到的技能是 solid 的，不是猜的"。

## 2. 两篇论文在说什么

### 2.1 《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》（2306.05685）

用强 LLM 当裁判评价开放式问答，并与人类偏好对齐率对照：

- **主结论**：GPT-4 判官与人类的一致率 **>80%**（单答案打分口径 85%，甚至高于
  人与人之间的 81%）（§4.2, Table 5）——LLM-as-a-Judge 可行。
- **三个已知偏差**（§3）：
  - **位置偏差**：交换两个答案顺序，判词会翻（GPT-4 一致率也只有 ~65%）；
    保守解法 = **换序判两次**，两次一致才算数（§3.2 解决方案）。
  - **冗长偏差**：往答案里塞"复读清单"就能骗过判官（Table 3）。
  - **自我偏好**：GPT-4 给自己的答案 ~10% 额外胜率（§3.1）。
- **数学/推理题判不动**：默认判官失败率 70%；两个修复——
  - **CoT judge**：让判官先自己作答再判；
  - **reference-guided judge**：先独立生成参考答案再放进判词 prompt，
    失败率 **70% → 15%**（Table 4）。
  - **few-shot judge**：带 3 条判例，一致性 65% → 77.5%（Table 12）。

### 2.2 《Semantic Evaluation for Text-to-SQL with Distilled Test Suites》（2010.02840）

回答"模型生成的 SQL 是真会，还是在这一个库里碰巧对"：

- 单库对答案（single denotation）有**假阳性**：语义错的 SQL 在这一个库上恰好
  同结果（Figure 1 prediction 1）。所以"换几份数据再跑，还同结果才算对"。
- **neighbor queries**：对 gold SQL 做单点扰动——换常量（34→35/33）、换比较符
  （> ↔ ≥）、换列名/字符串、删片段——生成一批"长得像但多半语义不同"的查询
  （§3.1, Figure 2）。
- **fuzzing + 蒸馏测试套件**：随机生成大量满足外键/类型约束的数据库，
  贪心保留能区分 gold 与 neighbor 的少数库（§4）。预测 SQL 在整个套件上
  与 gold 同结果才算对。
- **效果**：套件能区分 >99% 的 neighbor；人工核验 100 例全对；现有 Spider
  指标平均 2.5%、最差 8.1% 假阴性（§1, §6）。

一句话：**论文一证明"LLM 判官可用但会抖，要用机制校准"；论文二证明
"答对一次不算会，要在一组扰动输入上都对才算会"。**

## 3. MVE 已有机制 ↔ 论文方法对照

| 论文里的做法 | MVE 的对应物 | 状态 |
|---|---|---|
| LLM 判官与人对齐 >80%（§4.2） | 判官 = LLM（`MVE_CRITIC_MODEL`）+ 确定性闸门；判官只看材料账不看自述 | 已有 |
| **位置偏差 → 换序判两次**（§3.2） | 判官会抖 → **确定性判据先于判官**：搬运判据（60 字窗覆盖率）、引文逐字核验、`is_vacuous` 真空闸、`_material_real`。抖动的部分交给判官，能规则化的全部规则化 | 已有，且更狠（论文靠换序投票，我们靠"判据不抖"） |
| **reference-guided judge 70%→15%**（Table 4） | 判官 prompt 里先给**环境观察面/材料账**（真实行值、gh_tree+README、错误行号+返回形状），判官在事实上判，不裸判 | 已有——这正是论文里最有效的那个修复的同构 |
| **few-shot judge 65%→77.5%**（Table 12） | `reason_demos` 示范库：只收**验对**的判断过程（DeepSeek 拒绝采样口径），召回注入语义层 | 已有（2026-10-31） |
| 冗长偏差/自我偏好 | 未做专项校准；搬运判据部分覆盖"冗长复读"攻击（交原文=搬运，判未闭合） | 部分覆盖 |
| **neighbor queries：扰动 gold**（§3.1） | 骨架把一道题拆成 n 条维度，全闭合才算里程碑；追问/换题时题面自动变化 | 结构上同源，但**未系统化** |
| **换数据库回测**（§4，假阳性防线） | `generalize_sql_recipe` 已把技能泛化成 `:slot` 模板（存算法不存数值），消费侧 `_refill_sql` 回填——**天然支持换实体值重放** | **最大缺口：没有自动"换值回测"** |
| 技能利用率/失效标记（会上用户已做） | 技能带 命中/有效/失效 统计，复用错就标红 | 已有 |
| 判官会漏检错检（会议第 3 条） | 三闸设计本身承认这一点：规则闸 → 判官 → 随机性如实记录，不假装零漏检 | 口径一致 |

## 4. 佐证方案：用论文二的思路补上"换值回测"

按会议"结果能证实我们学到的不是猜的就行"的口径，最小落地是：

1. **技能入库后自动回测（neighbor 思路的 MVE 版）**：
   `learn_milestone_skills` 入库成功后，取该技能的 `:slot` 槽位，从环境观察面
   的**真实取值**里再挑 1~2 组与训练时不同的实体值（如换个部门、换个月份），
   用 `_refill_sql` 重放，判据仍用"取到真数 + 非真空"。
   - 全部通过 → 技能标 `verified`（solid 的证据）；
   - 任一失败 → 不删（可能是环境里没有对应数据），如实标 `unverified-variant`
     并记失败判词——对应论文的"区分失败 ≠ 必错，但要能看见"。
2. **判官对齐抽查（论文一 §4.2 的 MVE 版）**：定期抽样 N 条判官判决
   （判完成/判未闭合），人工复核一致率，记进 run_log 供面板展示。
   这是对"漏检/错检不可避免"的量化，不是消除。
3. **暂不做**：随机数据库 fuzzing（我们没有 gold SQL 可对照，MVE 的"gold"
   是判官+闸门，扰动回测已能提供论文二的全部防假阳性价值）。

## 5. 与论文的差异（如实记录）

- 论文一评测的是**单条 SQL 对 gold 的语义等价**；MVE 没有全局 gold，
  判据是"维度闭合 + 来源绑定 + 非真空 + 判官放行"，是过程性验证而非结果等价。
- 论文二是**离线评测基准**（人先出 80 题）；MVE 是**在线学习闭环**，验证机制
  内嵌在 propose → rollout → 记账 里（会议第 4 条：这正是导师认为我们更好的一点）。
- 两篇都不训练模型，与我们"模型外接"完全同构——换模型即测模型。

## 6. 会议演示中记录到的问题（备忘）

- 半年/多月聚合查询答不出：环境里没有对应数据（技能没问题，是数据边界）；
  换数据上传后可答 → 与"换值回测"方向一致。
- 上传表格问"几个员工"答 9/10 之差：判官对第一条技能卡得严、后续以
  "能取到数 + 不写死"为入库标准（用户原话），与三闸口径一致。
- MCP 不通导致部分学习失败：链路问题，不是学习问题。
