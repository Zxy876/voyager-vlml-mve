# 主循环对照：原版 Voyager vs 现在跑的 MVE（聚焦「修正自己代码 + 重试」）

日期：2026-10-23　｜　分支：`rebuild/fail-driven`（基线 `ac45d72`）
原版取证：`voyager_original/voyager/voyager.py`、`agents/{action,critic,curriculum}.py`
MVE 取证：`voyager_vlml/loop.py`、`voyager_vlml/agents/{action,critic,curriculum}.py`、`voyager_vlml/env/vlml_mcp.py`

## 零、结论（五条）

1. **「现在跑的」到底是哪一条循环，先钉死**：驾驶舱点启动 → `mve/pilot.py:464-473` 起的是
   `voyager_vlml/loop.py`。旧的 `mve/run_mve.py`（`loop_core.evaluate_vs_referee` 那条）**已冻结不调用**
   （`pilot.py:465-468` 写明原因）。所以本文的「MVE 主循环」=
   `loop.run_one_round` → `action.solve` → `critic` → 写技能库 → 记账。

2. **修正+重试的骨架是等价的**：写代码 → 执行 → 判成败 + 出 critique → **带着 critique 与上一轮的代码重写**
   → 上限内循环。三条用户最关心的点全部成立：谁重建 prompt（都是"下一步重渲染"）、重试在哪一层计数
   （都在"一个 task 之内"）、解析失败算不算一次失败（都算）。

3. **两处不等价，其中一处是实质的**：
   - (a) 原版**每步都重检索技能**（`voyager.py:256-260`，query 含本轮执行摘要），MVE **只在开跑前检索一次**。
     → 失败本身不会让检索变准。
   - (b) 原版回灌**整个观察**（`render_human_message(events=events)`，`voyager.py:262-268`），MVE 原来只回灌
     「取到几行 + 报错串」。→ **「没报错但取错列」这一整类错误修不了**。**本条已在本轮修掉**
     （`action.py:_render_last_result` + `render_iteration_prompt(last_result=)`）。

4. **判据不管口径**：`critic.check_task_success` 判的是「至少一次调用 ok 且取到真实值」
   （`critic.py:117-134`），**不判"取到的是不是题干要的那个量"**。所以「跑通 ≠ 口径对」不是重试坏了，
   是重试的**终点判断**没有这一维。

5. **回答「这一环没问题的话学习就没问题」**：结构上没问题；学习现在的问题**不在循环结构**，
   在两个口子 —— ①修正时看不到自己取回了什么（已补）②成功判据不校验口径（待补闸）。
   昨天实跑把 `round_number=1` 当首血还入库，就是这两条叠加的结果，不是重试次数不够。

## 二、三个关键点细判

### 2.1 谁拿 critique 重建 prompt

两边都是**下一步重渲染**，不是"把 critique 追加进对话历史"：

- 原版：`check_task_success` 返回 `(success, critique)` → `render_human_message(critique=critique)`（`action.py:197-200`
  的 `Critique:` 槽）→ 赋给 `self.messages[1]`（`voyager.py:270`）。**每步只有两条消息**，旧的被覆盖。
- MVE：`critic` 返回 `(ok, critique)` → 下一轮 `write_sql(critique=...)` → `render_iteration_prompt` 的
  「上一轮的环境反馈：」。

**结论：等价。** 都是"用批评覆盖式重建一次输入"，不会无限堆历史。

### 2.2 重试上限在哪一层计数

| 层 | 原版 | MVE |
|---|---|---|
| 一个 task 内 | `action_agent_task_max_retries = 4`（`voyager.py:30`），在 `step()` 里数 | `max_iters = 3`（`loop.py:466`），在 `solve()` 里数 |
| 一个 task 之上 | 无（失败就交回 curriculum 换题） | `run_rounds` 的 `while True` **不停**（`loop.py:614`）；新分支 `task_intake.next_focus` 换子目标 |

**结论：层次一致，MVE 少 1 次。** 有没有必要补到 4？实测 3 次内 90% 的"列名猜错"都能修（错误串直接给列名）；
真正修不动的是口径错，而口径错**再给 4 次也修不出来**（除非回灌结果，即 §2.3）。所以先不调数值。

### 2.3 解析失败算不算一次失败

- 原版：`Trying again!` 之后照样 `self.action_agent_rollout_num_iter += 1`（`:276` 在 if/else **之外**）
  → **算一次**，也**不加 critique**（critique 变量没赋值，仍是上一步的）。
- MVE：`continue`，但 `for i in range(max_iters)` 的 `i` 已经推进 → **算一次**，且**给了 critique**
  （"请只输出一条以 SELECT 开头的查询"，`action.py:237`）。

**结论：等价（MVE 略优）。**

> 顺带纠正一个容易误读的点：原版 `critic.check_task_success(max_retries=5)` 的 `max_retries`
> 是**critic 自己 JSON 解析失败的重试**（`critic.py:94-117`），不是"判 5 次成败"。

## 三、实质差异 A：技能检索不随执行结果刷新

原版（`voyager.py:256-260`）：

```python
new_skills = self.skill_manager.retrieve_skills(
    query=self.context + "\n\n" + self.action_agent.summarize_chatlog(events)
)
system_message = self.action_agent.render_system_message(skills=new_skills)
```

MVE（`loop.py:454-470`）：`skill_hits` 在 `solve()` **之前**算一次，之后每一轮 `write_sql` 都用同一份。

差别不在"带不带技能"（两边每轮都带），在 **"带哪几条技能"**：

- 原版的检索键里含**本轮执行摘要** → 第 2 步检索到的是"我刚砍了木头，接下来该做什么"的技能。
- MVE 的检索键是**题面文本**，失败不会改变它 → 第 2、3 步拿到的还是同一批。

对 VLML 这种"一题一条 SQL"的形态，影响不大（一题就一个动作，没有"下一步"）。
对**多步任务**（比如算工资要先查人事表再查绩效表）影响就大了：第一步失败了，第二步还在拿同一批配方。

**判定：现在可以不改，但一旦 task 变成多步（>`solve` 单条 SQL），这条必须先补。** 补法很小：把
`_retrieve_skills` 挪进 `solve` 的循环里，query 用 `question + 上一轮 error/结果摘要`。

## 四、实质差异 B：回灌的信息不全（本轮已修）

### 4.1 问题

原版把**整个观察**回灌（`render_human_message` 里有背包、位置、`Execution error:`、`Chat log:` 等），
模型能看见"我这一步到底改变了什么"。

MVE 原来只回灌两样：`critique`（= 行数 + 报错串）和 `last_sql`。于是：

| 失败类型 | 能不能修 | 为什么 |
|---|---|---|
| SQL 语法/列名错 | ✅ | critique 里有 `Binder Error: no such column: xxx`，列名直接可见 |
| 空结果（0 行） | 🟡 | critique 说"口径或过滤条件可能不对"，但看不到返回了什么 |
| **有数但取错列/错口径** | ❌ | critique 说"取到 N 行 —— 方法跑通了"，**结果本身又没给模型看** → 模型没有任何依据发现"我取的不是题干那个量" |

第三行就是昨天实跑的现场（`docs/外部task闭环.md` §7.2）：把 `round_number = 1` 当"首血"，
SQL 跑通、取到数、critic 判成功、错配方入库。

### 4.2 修法与实测

`voyager_vlml/agents/action.py`：

- 新增 `_render_last_result(obs)`：把上一轮返回的**列名 + 前 3 行**渲染成文本（兼容
  `{columns:[...], rows:[[...]]}`、`[{...}]`、空集、报告型 dict 四种形态）。
- `write_sql(..., last_result=)` → `render_iteration_prompt(..., last_result=)`，在「上一轮的 SQL」与
  「上一轮的环境反馈」之间插入「**上一轮这条 SQL 实际取回的结果**」。
- 迭代指令补一句：*"改之前先对照任务和上一轮取回的结果：如果取回的列不是题干要的那个量，
  说明表的选法或口径错了，别再在原句子上微调。"*
- `solve()` 里失败后 `last_result = _render_last_result(obs)`，并在日志打一行 `[回灌] 上一轮取回：…`。

实测渲染（本地跑的，非口头）：

```
列：round_id、fb_team、round_number
行：round_id=r1，fb_team=NRG，round_number=1
行：round_id=r2，fb_team=LOUD，round_number=1
```

空集与报告型也验过：`（结果为空集，0 行）` / `列：summary　行：summary=NRG 3:1`。

## 五、判据的两个洞

`critic.check_task_success`（`critic.py:117-134`）= `至少一次 ok` ∧ `rows ≥ 1` ∧ `有真实值`。

- **真空洞（已堵）**：纯聚合在空表上返回 1 行 `(NULL, 0)`，行数判据被骗过 →
  `is_vacuous` 收紧为"至少一个真实值"（`critic.py:90-107`，注释里记着 2026-10-14 那次事故）。
- **口径洞（未堵）**：`round_number=1` 当首血、拿 `agg_*` 空表的 0 当答案，只要"有真实值"就判成功。
  这一维**判据本身没有能力**：它只有观察，没有题干的语义。
  → 需要第二道闸（`intent-diff`：SQL 的过滤/聚合 vs 题干与节点 `skills` 的承诺），或把成功判据改成
  「必须有一条 node.skills 里点名的表/字段出现在 SQL 里」。

**结论：这一环不是"重试"的问题，是"终点"的问题。** 加多少次重试都补不上；判定成功那一刻必须多问一句
"这是题干要的量吗"。

## 六、对验收线的影响（有数据源、无建模表）

验收线原话：*有数据源（rib，vlgg）无建模表（vlml），看它能不能自己学会完成外部 task、积累技能，
自己积累的知识图谱能长成一个类 VLML 的表。*

### 6.1 已经成立的：结构是"实查"的，不依赖 VLML 建模表

`env.schema_block()`（`vlml_mcp.py:142-235`）**直接查 `information_schema.columns`**，并且：

- 每张表带**行数**，0 行的表明写 `**0 行 · 空表，查它只会得 0 行，别查**`（`:224-227`）；
- 每张有数据的表给**一行真实样例值**（`:187-215`），解决"布尔列被当字符串比""side 是 attack 还是 T"这类猜值；
- 有数据的表排前面、空表沉底（`:231-235`）；
- 注释里明说：*VLML 自带的列级口径 `column_definitions.yaml` **只覆盖 3 张表**，指望不上*（`:191-192`）。

也就是说：**"没有建模表"这件事，取数那一侧早就自己解决了** —— 它从来没读过 VLML 的建模表，
schema 是运行时摸出来的。换成 vlgg 或客户的工资库，这一侧不用改。

### 6.2 还没成立的：原语清单是硬编码的 rib 语义

`control_primitives/sql_primitives.py` 的 `render_primitives()` 会整段进写码 prompt，里面写死了：

| 行 | 内容 | 换库后的后果 |
|---|---|---|
| `:33` | 例：`SELECT COUNT(*) FROM rounds WHERE series_id = '2843069'` | 模型以为有 `rounds` / `series_id` |
| `:36` | "数回合用 `COUNT(*)`，不要用 `SUM(round_number)`" | 与工资库无关，纯噪声 |
| `:37` | "地图列叫 `map_name`；**没有 teams 表**" | **直接误导**：新库若有 teams 表，模型反而不敢用 |
| `:48-94` | 7 个 `*_report(series_id=…)` / `scouting_report(team_name=…)` | 这些是 VLML **建模层**的报告工具，新库没有 → `env.call` 返回"未装载"，白烧一轮 |

**判定：这正是"学习方向不变、数据源可变"的破口。** 前 3 行是"VLML 世界的经验"被当成通用原语，
第 4 组是把 VLML 建模能力当成默认存在。要过验收线，`render_primitives()` 得改成**由当前库实查结果生成**
（`query_sql` 一条 + `get_database_info`，其余报告工具按 `env.has(name)` 过滤），而不是静态清单。

### 6.3 所以"类 VLML 的表"能不能自己长出来

能长出来的部分：图谱节点（知识点）→ 每节点一条可复用 SQL（技能）→ 检索复用。这条链不依赖建模表。
**长不出来的部分**：VLML 那张表真正值钱的不是"有哪些列"，是**列的口径**（`round_won` 是 bool 还是字符串、
`fb_team` 是"首血的队"还是"首血来自哪队的选手"）。这一层现在只能靠 `schema_block` 的**一行样例** +
节点 `skills` 里人写的一两句话。所以：

> 验收线能不能过，取决于**学到的东西里有没有沉淀口径**，而不取决于图谱节点数。
> 现在的 `skill_store.add(code=sql)` 只存 SQL，不存"这条 SQL 为什么这么写"——
> 同一个坑下次换张题还会再踩一遍。

## 七、怎么验（下一步）

1. **修 A/B 两处后的对照实跑**（rib，同一个 fail 的 task）：
   - 关掉 `last_result`（改回空）跑 3 次 → 记录第 1/2/3 轮 SQL 与是否收敛；
   - 打开 `last_result` 跑 3 次 → 同口径记录。
   判据：**口径错的收敛率**（第 2 轮把"取错列"改掉的次数），不是"最终有没有取到数"。
2. **换库冒烟**（vlgg 或人工小库）：只验 `schema_block` + `render_primitives` 是否还把模型带偏 ——
   看第 1 轮 SQL 里出现的表名是否 100% 来自 schema。
3. **口径闸**：先离线跑 `intent-diff` 的判定（不接学习环），拿昨天那条错配方做样本，
   看它能不能把 `round_number=1` 判成 drift。

## 八、剩下两刀（与 `docs/外部task闭环.md` §7.3 同一份账）

| # | 刀 | 位置 | 为什么必须 |
|---|---|---|---|
| 1 | 学习前预检"表有没有行" | `curriculum.propose_next_task` / `task_intake.subtopics_of` | 现在会让子目标挂在 0 行表上，学 3 次 stale 就永远学不完，`retry` 不可能成功 |
| 2 | 成功判据加口径检验 | `critic.check_task_success` 之后，或 `skill_store.add` 之前 | 不拦就会把错配方固化，越学越错（已有实证） |
