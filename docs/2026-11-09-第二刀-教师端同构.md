# 第二刀：教师端同构（落点固化）—— 实施记录

> 2026-11-09。本文档记录「把消费侧的五/六个根因按 maieutic 同构修掉」的
> 实施过程、取证与踩坑。**所有结论都有服务器实跑证据**，不写「应该」「可能」。
> 仓库：`Zxy876/voyager-vlml-mve`。分支 `feat/learn-upload-path`。

---

## 0. 为什么要做这一刀

用户拍板的方向：

> 「其实你把教师端同构看作学习时的课程规划就好啦。这样就可以照搬 maieutic
> （voyager 组件 prompt 换血；现在可能已经这么做了）然后第五根因更本质是
> prompt 和守卫的问题，你换完 maieutic 的血做完同构也会改善，我相信守卫也能在
> maieutic 找到同构」
>
> 「你按照我说的开始开工；按照 maieutic 同构（其实就是抄和换血）」

**同构的对象不是「学习算法」，是「教师端把环境约束一次性说清」这件事。**

原版 maieutic 的依据（`~/maieutic` 只读取证）：

- `src/lib/opus/prompts/scaffolding.ts:262 buildScaffoldingUserMessage` 把
  **targetUnit / targetLanguage** 告诉骨架生成器 —— 即「这个学生学过哪些工具」
  这条**环境约束**；并明写
  「Do NOT include dimensions whose only defensible answer requires tools the
  student hasn't learned」。
- 于是维度**必然落在够得着的工具上**，运行时只读不重拆。
- 教师端生成一次 → publish 快照进 `Exercise.specGateDimensions`
  （`src/app/api/author/generate-scaffolding/route.ts:29-45`）；
  `src/` 内 `prisma.exercise.update/upsert/delete` 零命中，只有 `create`
  （`sessions.ts:48`）→ **运行时只读不重拆成立**。

MVE 的同构物 = 「本场景消费侧真查得到哪些表」。这就是 `mve/reachable.py`。

## 1. 现场取证：根因在教师端，不在消费侧判据

服务器 `43.161.203.50:/root/mve`，场景 L 实查两个库：

```
/root/mve/scene_data/L/scene.duckdb       -> ['web_docs', 'web_facts']   ← 数据源（SQL 连这个）
/root/mve/scene_data/L/web_ledger.duckdb  -> ['web_evidence']            ← 账本（另一个文件，SQL 连不到）
```

场景 L 的三份真实骨架（`mve/ckpt_maieutic/L/*.json`）：

| 文件 | 问句 | 维度落点 | 消费侧判定 |
|---|---|---|---|
| `2776f86718d1` | 「帮我查查用户名 ce 的这位女生…」 | 全写「在 **web_evidence** 表中」 | `db=False infer=True` → **什么都不查** ❌ |
| `77636f315f0e` | 「username为ce的女生…用Sherlock找」 | 全写「在 **web_facts** 表中」 | `db=True` ✅ |
| `7f3b9415c90b` | 场景 B 的工资题误落 L | `information_schema.tables` / `up_工资明细` | `db=False`（L 里真没有，正确） |

**根因链**（逐环取证，不是推测）：

1. `maieutic_scaffold.scene_sources()` 把 `web_ingest.ingest_state` 的**第 ③ 段**
   一起展示给出题器，而那段原文是「审计账本 EAV：属性名与取值域在这里最全 ——
   宽表是 PIVOT 出来的」→ 出题器据此拆出「去查账本表」的维度。
2. 而 `web_ingest.py` 文件头的设计原话是：「账本不该是学习目标，所以搬到数据源
   之外，只留摊平后的宽表」→ **账本不是学习目标，出题器却看到了它**。
3. `scene_profile.source_tables()` 只列**数据源表** → 消费侧认不出账本表。
4. 旧的两张关键词表（`_mentions_upload` / `_mentions_external`）在真实数据上
   **从未命中**（真实维度全是「在 X 表中」形式），却**误伤** ——
   「在 web_evidence 表中查…」既不命中表名也不命中那些词 → 整题落进 infer。

⚠️ **附带纠错**：`mve/local_agent.py:1367` 的注释声称材料账同构于原版
「助产士的口径（`src/lib/research/agent.ts`）」—— **原版仓库里没有这个文件**
（`~/maieutic` 全仓无 `src/lib/research/` 目录、无 `gathered`、无任何
`web_search|fetch`）。**勿再当依据**；原版运行时只有
`src/lib/run-exercise-code.ts`（跑代码 → stdout/stderr）。

## 2. 第二刀 B：落点固化到骨架

### 2.1 可达表单一事实源 —— `mve/reachable.py`（新建）

```python
LEDGER_FILE = "web_ledger.duckdb"
def reachable_tables(scene_id) -> list[str]   # 消费侧真查得到的表（数据源库实查）
def ledger_tables(scene_id)   -> list[str]    # 账本表（另一个库，不可直接查）
def all_visible_tables(scene_id) -> list[str] # 可达 + 账本（给骨架生成器看的完整清单）
def is_reachable(scene_id, table) -> bool
def unreachable_in_text(scene_id, text) -> list[str]   # 文本点名了「真存在但查不到」的表
```

### 2.2 教师端改动 —— `mve/maieutic_scaffold.py`

- `scene_sources()` 新增**第 ⓪ 段**「可查询的表（**维度只能落在这些表上**；
  别的表不在数据源里，查不到，不许当落点）」—— 原版 `targetUnit` 的同构物，
  放在最前。
- `SCAFFOLD_SYSTEM_SOURCES` 增加「每条维度必须带 `landing` 字段」段。
- `SCAFFOLD_SYSTEM` 的 dimensions schema 增 `"landing"`。
- `_clean_dims` **保留** `landing`（原版丢弃）。

> ⚠️ **落点字段不能叫 `source`**：原版 `SpecDimension` 只有 4 字段
> （`id/description/rationale/source`），其中 `source` = 「这条维度是谁写的」
> （`Source` ∈ `{opus, instructor_edited, instructor_added}`，
> `schemas.ts:33`），**不是数据落点**。故 MVE 特有扩展命名为 `landing`。

- `mve/web_ingest.py`：`ingest_state` 的账本段**明说它查不到**。

### 2.3 消费端改动 —— `voyager_vlml/consume.py`

- **删掉** `_mentions_upload` / `_mentions_external` 两张关键词表
  （与文件头「不猜题型、不写关键词表」自相矛盾）。
- `_plan_from_scaffold` 路由改读 `landing`：
  可达表 → `db` / 远端抓手 → `web` / 上传文件 → `file` / `none` → `infer`；
  **写错了的落点 → 记进 `unreachable_landings` 并如实交代**（不静默降级）。
- 旧骨架（无 `landing`）→ 回退**字面判据**（可达表 / 远端抓手名出现在维度文本里）。

## 3. 第二刀 A：消费侧接来源绑定守卫

**问题**（生产实证，H 场景 2026-10-31）：维度问「README.md 里的仓库最后更新时间」，
执行层调 `gh_repo_info` 拿仓库元数据的 `updated_at` 当答案 → 旧判据只问
「取到没有」→ 闭合 → 里程碑全亮。**材料是真的、来源是错的。**

学习侧当时补了 `source_binding`（`learn_orchestrate.py:1716`），**消费侧没有**。

修法：消费侧调**同一份实现**（`mve/source_binding.py` 的 `check`）：

```python
def _source_binding_gate(question, evidence, db_path, *, dims=None) -> tuple[bool, str]:
    import source_binding as _sb
    ...
    ok, why = _sb.check(t, evidence, db_path)   # 判据看 args，不看返回文本
```

插入点：`_grade_substance` 之后、`_fits_judge` 之前 —— 先确认「取到了真数」，
再确认「取的是不是这一份」。

**不新增 LLM 调用、不新增门槛机制**：消费侧完成判定仍是
`critic_ok = data is not None`（确定性）。

## 4. 补洞：旧骨架（无 `landing`）也要能判出「落点够不着」

现场唯一存在的坏骨架**是第二刀之前生成的**，它**没有 `landing` 字段**：

- `resplit_needed` 只看 `landing` → 对它恒返回 False → 人看不到「该重拆」
  的信号 → 坏骨架永远留在缓存里；
- 消费侧旧骨架路径两条判据都不命中 → 整题**静默**落进 infer = 什么都不查，
  **且没有任何交代**（人只看到「答不出来」）。

修法（判据仍是**实况**，无关键词表）：

- `reachable.unreachable_in_text(scene_id, text)` —— 文本里字面点名了
  「**本场景真存在、但消费侧查不到**」的表（账本表，实查 `ledger_tables` 得知）。
  ⚠️ 刻意**不**用「不在可达表里就算不可达」：那会把「场景里根本没有的表名」
  误判成落点写错。判据必须是「这张表真存在，只是搬到了另一个库」。
- `resplit_needed` 补第二条判据；消费侧旧骨架路径也把它记进
  `unreachable_landings`（与新骨架走**同一条交代路径**）。

### 4.1 顺带踩到的真实隐患：`_cache_path` 的键会变

`_cache_path` 的键 = `md5(问句)[:12] + "_" + md5(db_path)[:8]`，db_path 来自
`scene_profile.profile()`。对一个**还不存在**的场景：

1. 第一次调用：场景目录里还没有 `.duckdb` → `kind=local`、`db_path=""` → 键 A；
2. `resplit_needed` 内部先调 `reachable_tables` → `ensure_source` **现场建**了
   一个 `scene.duckdb`；
3. 第二次调用：db_path 变了 → **键 B**。

→ 写文件的路径是 A、读文件的路径是 B → `p.exists()` 恒 False →
判据永远读到「文件不存在」。**真实场景的 db_path 是稳定的**（实测 L 两次调用
同路径）。已加回归断言（`test_landing_gap.py` 第 5 段「同一把钥匙」）。

## 5. 作废入口（显式，人触发）

骨架「拆一次就固定」是铁律（按失败指纹重拆 → 维度 id 每轮变 → 闭合账全对不上，
2026-10-26 生产实测）→ **不能自动重拆**，必须有显式入口。

- `maieutic_scaffold.invalidate_skeleton(scene_id, question)`：
  作废 = **改名留证**（`x.json` → `x.invalidated<ts>.json`），不删。
  **进度账不迁移**（那批闭合是对着错落点做的，本就不该算数；且新维度 id
  必变，迁移只会造成「已闭合被当成未闭合重跑」）。
- `mve/dashboard.py` 新增 `POST /api/milestone/invalidate`
  （payload `{scene_id, question}`）。

## 6. 生产实证：重拆失败 → 挖出「思维链吃光 max_tokens」

作废坏骨架 → 触发重拆 → **5 次重试全失败**，报
「LLM 输出里没有可用维度（解析失败/空列表）」。

逐层取证：

1. **prompt 完整** —— system 2746 字、material 4075 字；可达表清单、landing
   要求、账本表「查不到」的标注**全都在**。
2. **LLM 其实读懂了** —— 它的输出里正确指出
   「web_evidence 表在另一个库 web_ledger.duckdb 里，不许拆出查 web_evidence
   的维度」「可用数据源只有 web_docs, web_facts」，还规划了 landing。
3. **但它输出的是长篇思考散文，不是 JSON。**

根因：**GLM-4.6 默认开着思维链，思考段与正文共用 `max_tokens`**。
实测对照（同一 prompt，`prompt_tokens=3486`）：

| 方案 | finish_reason | content | reasoning | 维度 |
|---|---|---|---|---|
| 不传 thinking | **length** | **0** | 2400（吃光） | **0** ❌ |
| `thinking={"type":"disabled"}` | stop | 1781 | 0 | **4** ✅ |

关掉思考后，模型不但给出了 4 条维度，还**全部落在可达表上**
（`web_facts` ×3、`web_docs` ×1），`material_note` 里自己写明
「web_evidence 是审计账本不在当前可用数据源中」。

**修法改在模型适配层**（不是改 prompt、不是改判据）：

- `mve/llm_client.chat` 加 `thinking` / `response_format` 两个**可选透传**参数
  （各调用点自己决定；没硬编码进 `chat`）。
- `maieutic_scaffold._default_llm` 传 `thinking={"type":"disabled"}`。
  ⚠️ **只关出题器**：判官（`reason_pass` / `task_critic` / `voyager critic`）
  需要深思，**不动**（有测试钉住）。
- 失败原因要**说清是什么**：`llm_client` 空内容时区分
  `finish_reason=length`（思考吃光预算，**可修**）与「模型真的什么都没说」
  （**不可修**）；`maieutic_scaffold._call_llm` 的失败原因里带上方向提示。

## 7.1 消费侧实跑：两次对比（同一道题，服务器真实跑）

| 指标 | 修之前（08:53 / 12:59） | 修之后（13:06） |
|---|---|---|
| `plan_routes` | `db=True`（旧骨架） | `db=True`（新骨架，4 条维度落在可达表） |
| `ok_tool_calls` | **0** | **6** |
| `judgment_result` | `fetched_empty` | **`written`** |
| 「来源未绑定」出现在 reuse_errors | ✅ 是 | ❌ **不再出现** |
| answer | 「这题这轮没答出来 —— 不编数」 | 带真数据的结构化答案 |
| Sherlock 原始探测 | 未落进答案 | **462 站 / 123 CLAIMED / 272 AVAILABLE** |

三处修复各自的效果都可分辨：

- **取数守卫换血**（第一刀）→ Sherlock 返回的 dict 不再被「必须长得像 SQL 形状」
  的闸丢掉；
- **来源绑定守卫 + 上游等价放宽**（第二刀 A）→ 原来判「来源未绑定
  （这条问题点名了表 web_facts，但本轮一步都没取它…）」把整轮判死；
  放宽后（web_facts 就是 Sherlock 结果落库后的摊平宽表 → 同一份数据）
  → 放行；
- **落点固化**（第二刀 B）→ 维度自带 `landing`，路由不再落进 infer，
  落点够不着时**如实点名**而不是静默降级。

### 7.2 仍未闭合：已学技能库里的「坏落点技能」

场景 L 的 11 条技能里，**3 条点名了 `web_evidence`**（另一个库，SQL 连不到）：

```
web_evidence_bio_verification
web_evidence_http_status
web_evidence_source_urls
```

它们是**第二刀之前**对着坏落点「闭合」的技能（面板日志 08:47-08:52：
「维度闭合 3/3：在 web_evidence 表中…」）。消费侧复用它们时返回空
（`claimed_platforms: []`），**盖住了**同轮 agent 现做拿到的真数据
（Sherlock 原始探测摘要里有 123 个 CLAIMED）。

系统**已经正确降级**（日志：「已检索到已学技能但组合没取到真数 →
SQL 通道没成 → 改由 agent 写代码（query_sql）取到数」→ agent 拿到了真数据），
所以不是崩溃、也不是假闭合 —— 只是**结构上老技能的位置是空的**。

**建议修法（第三刀，本次未做）**：技能复用前检查它的 code 点名的表
**现在还可达吗**（用第二刀建好的 `reachable.reachable_tables` +
`ledger_tables`）→ 不可达就**不复用**（如实不记/不用），退到现场现做。
判据仍是实况（可达表清单），无词表；且与「来源绑定的上游等价」同一口径。

**为什么本次不做**：它是独立的一刀（动的是技能复用路径，不动判据），
且「清掉那 3 条坏技能」是**破坏性操作**，该由人决定（面板有
「🗑 清本场景」）。
