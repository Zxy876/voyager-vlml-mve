## 1. 功能改造（feat）

### 1.1 技能合成（composition）——同构原版 Voyager
原版取证：`voyager/agents/skill.py` 的 `programs` = primitives + **全部技能代码**（具名函数）；
`env/mineflayer/index.js:253-256` `eval(programs + "\n" + code)` —— 技能与新代码**同一作用域**，
trial1 的 51 条技能里有 7 处「技能调技能」；prompt `action_template.txt:39`
"Reuse the above useful programs as much as possible"。

MVE 同构实现（`64e5b4d` + `bc008aa`）：
- `mve/local_agent.py:_make_skill_fn` —— 每条已学技能包成 `skill_<name>()` **注入执行域**
  （不是只贴进 prompt），模型可写 `RESULT = {"定义": skill_def(), "起源": skill_origin()}`；
- `solve(require_skills=True)` —— 命中（HIGH/MEDIUM 置信）的题**必须**调用已学技能，
  不强制模型一律凭记忆写（实测给了 2 条可调用技能它仍交记忆版）；不达标判不通过并重写一次；
- 检索键必须是**本题归题结果** `topic_id`（`voyager_vlml/consume.py:_retrieve_skills`）——
  传空 topic_hint 会按词面挑到别人那批技能，出现「命中却用到 0 条技能」。

### 1.2 图谱归属：一次导入 = 一个父节点（`14ab056` + `827e820`）
- 图谱挂 import 批次、技能记 `blueprint.import_id`；归属展示一律走**反查**
  （`blueprint.import_id` → 技能数、`imports_of` → 批次），不另存一本账（同 Obsidian）；
- 面板：技能卡标「哪次导入/哪个里程碑长的」，导入记录标「这批长出几条技能」（`7375e77`）。

### 1.3 可达性真判与可观测（`28a5d66` + `a02ab69`）
- 可达 = 整条循环：技能回注执行层 + 追问历史跨次累积（改自一次性三态判定）；
- 学习侧回注已学配方可视化——「能力边界」看得见。

## 2. 稳定性修复（fix）——按「同一个症状叠了三层」主线

用户报障形态：**「技能库里有这个技能，消费却用不上」→ 面板显示 `工具 0 次 · 0 行 / 取到真空`**。
排查发现同一症状底下叠了三层独立 bug，逐层剥开：

### 第①层：技能重放没继承事件循环（`776e045`）
- 症状：`RuntimeError: 已学技能 style 重放失败：NameError: name 'mcp_neko_web_search' is not defined`
- 根因：外层 `solve` 在事件循环线程建命名空间 → mcp_* 注入成功；但技能函数在
  `_run_restricted` 的 **worker 线程**里重建命名空间，`_ns_base` 不传 loop 时
  `get_running_loop()` 抛错被吞 → mcp_* 一个都没注入。
- 修：solve 捕获 `get_running_loop()`，经 `_build_skill_fns → _make_skill_fn → _ns_base(loop=…)` 一路下传。

### 第②层：消费侧墙钟 30s 掐死多条技能串行取数（`a254d05`）
- 症状：5 条技能全部进了 trace，但 `errors: ["执行超时（>30s）"]`、rows 0。
- 根因：consume 调 `_la.solve()` 没传 timeout；每条技能都是一次真实联网取数（5~20s），
  5 条串行 40~100s。
- 修：`_consume_timeout(n_skills)` = 30 + 25×条数，封顶 180s，env
  `MVE_CONSUME_TIMEOUT` 可覆盖；③b 合成与 ③a 单条直接重放都改用它。

### 第③层：MCP 网关连接绑死在旧循环上（`fc41f7b`）
- 症状：**重启面板后第一次导入能通、之后全部超时**（5 条重放全 `>55s`）——
  同一分钟里走本机 `web_search` 原语的另一条导入却是通的。
- 根因：stdio MCP 的 transport / `_read_loop` 绑在**连接时的那个循环**上；
  面板每次导入 `asyncio.run()` 起新循环（`dashboard.py:3187`），网关却是进程级单例 →
  第二次导入起，`connected_servers()` 非空 → 跳过重连 → 把调用桥到已关闭的旧循环。
- 修：`MCPClient.loop` 记录连接时循环；`connected_servers(loop)` 只算绑当前循环的连接；
  `stale_servers(loop)` + `ensure_mcp_tools` 发现死连接就 `disconnect_all()` 整批重连。
- 取证方法（下次照抄）：看 `/proc/<pid>/fd` 是否指向 `(deleted)`/旧循环、看 coach_log
  `errors` 里的超时条数、对比「是否只有第一次成功」。

## 3. 面板性能与驾驶舱（2026-10-21）

### 3.1 黑客松面板挂死（`5d28684` + `4b5d579`）
- 现象：`https://…:8443/mve-hackathon` 打开即 `Unexpected end of JSON input`。
- 取证：py-spy 抓栈 —— 几十个线程卡在 `probe_env` / `_load_raw`，VmRSS 3.17G（机器 3.6G）、
  77 个 duckdb fd；cProfile 单独跑 `build_state()` = **13.7s**，其中 `skill_store._load_raw`
  占 12.8s —— 一次 `build_state` 里 `all_skills()` 被调 **5 次**，每次全量解析
  **110MB** 的 `skill_store.json`（878 条 × 每条约 93KB，大头是每条 4096 维 `emb` 原样存 JSON）。
- 修（三处，缺一不可）：
  1. `build_state` **单飞 + 3s 缓存，缓存按场景 id 分桶**（只按时间 → 切场景读到上一份，
     `test_scene_isolation` 9 项失败），失败/超时也返回合法 JSON（`pending` 标记）；
  2. `probe_env` 15s 缓存（每次探测新开 duckdb 连接，一个 build 调两次）；
  3. `skill_store._load_raw` 按 `(mtime_ns, size)` 指纹缓存；`_save()` 后把写盘对象塞回缓存；
     外部改文件指纹变仍会重读。
- 前后对比（重启后实测）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `/api/state` | >25s 永不返回 | **0.011s** |
| `/api/graph` | 150s 超时 | **0.034s** |
| 进程 RSS | 3.0G | **233MB** |

### 3.2 驾驶舱「日志怎么没了」（`9eda531`）
- 取证：`/proc/<pilot>/fd` 与 `/proc/<scene_learn>/fd` 全部指向 `pilot.log (deleted)` ——
  循环运行中点「清空日志」，`unlink` 后两个进程继续往**已删除的 inode** 里写，
  文件再也不会出现，整轮日志全丢。
- 修：`clear_log()` 运行中（`running` 或 `child_pid` 在）拒绝并说明；前端 alert 原因。

## 7. 诚实边界与待办（未做完的都列出来）

1. **数学场景能力成色**：Scene I 的 14 条技能全是 `mcp_neko_web_search` 配方 ——
   数学「学会」目前是"会搜"不是"会算"。要真泛化到数学能力，出题器需把维度落成
   本机计算/SQL 可达的抓手。
2. **多技能合成的成功实例**：机制有测试钉死，但"复用优先"（③a 第一条配方取到数就收工）
   使 ③b 合成几乎不触发；主库尚无修好后的多技能成功实例。可选改造：综合题（多维度
   归题）优先走合成，避免"1 个搜索结果撑 4 个子问题"。
3. **`skill_store.json` 110MB 的设计问题**：`emb` 4096 维按 JSON 数字存，可改
   base64 float32（110MB→约 15MB）。
4. **`/api/state` 单次 1.1MB**（`series` 725KB），前端 4s 拉一次，可做增量。
5. **`systemctl restart mve-panel` 会连 Popen 的 pilot/scene_learn 一起杀**
   （systemd cgroup），`pilot_state.json` 残留 running —— 待选：`setsid` 脱离
   cgroup 或启动时核对 pid 真伪。
6. **失败维度回流选题**（原版 `failed_tasks` 回灌）与**出题粒度**（7 维大题 vs
   单维度小题）仍为待议设计。
